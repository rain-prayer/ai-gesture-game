# 架构设计

> 这份文档解释"代码为什么长这样"：分层、线程、状态机、物理与数据格式，以及当时的取舍。

## 1. 分层

```
┌────────────────────────────────────────────────────────────┐
│ 采集层   摄像头 → OpenCV 取帧（640×480）                     │
├────────────────────────────────────────────────────────────┤
│ 识别层   MediaPipe HandLandmarker → 每只手 21 个关键点        │
├────────────────────────────────────────────────────────────┤
│ 逻辑层   手指伸直计数 → open/fist → 双手组合 → 去抖/边沿/迟滞  │
├────────────────────────────────────────────────────────────┤
│ 控制层   跳跃 / 下蹲 / 二段跳 / 暂停 / 继续                    │
├────────────────────────────────────────────────────────────┤
│ 表现层   Pygame 渲染 + 物理碰撞 + 粒子 + 音效 + 菜单/存档/商城 │
└────────────────────────────────────────────────────────────┘
```

（配图：[docs/images/architecture.png](images/architecture.png)）

## 2. 线程模型

| 线程 | 职责 | 频率 | 产出 |
|------|------|------|------|
| `GestureFeeder`（daemon 线程） | 打开摄像头、逐帧推理、去抖状态机 | 摄像头帧率（约 30 fps） | `raw` / `stable` / `camera_ok` |
| 主线程 | 事件处理、物理、碰撞、渲染、UI | 60 FPS（`pygame.time.Clock` 锁定） | 画面与声音 |

两个线程只通过 **一个字符串状态 + 一个布尔标志** 通信，没有共享可变游戏对象，因此不需要锁。

设计原因：

- MediaPipe 推理（约 9 ms）+ 摄像头读取是阻塞的，放进主循环会让画面掉帧；
- 手势去抖需要"连续 N 帧一致"，天然适合放在采集线程里；
- 主循环只需要"当前稳定的手势"，不关心中间过程。

异常处理：摄像头打不开 / 连续约 1 秒取不到帧 → `camera_ok = False`，线程退出；主循环照常运行并显示"未检测到摄像头"提示，键盘仍可试玩。

## 3. 状态机

### 3.1 手势状态（采集线程）

```
raw = 分类(当前帧)
if raw == candidate: count += 1
else: candidate = raw; count = 1
if count >= 4: stable = raw        # 去抖
```

### 3.2 游戏状态（主线程）

```
start ──点击"开始游戏"/空格──> play ──生命耗尽──> over ──重来──> play
                                 │  └──碰到终点旗──> win（90 帧后结算）
                                 ├──2 指──> paused ──1 指/点击──> play
                                 └──Esc──> 退出
```

菜单内部还有 `main / save / diff / mode / shop` 五个子界面，用鼠标点击切换；返回键统一回到 `main`。

### 3.3 动作触发

- **跳跃**：`open` 的上升沿 + 角色在地面；
- **二段跳**：`two_palms` 的上升沿 + 角色不在地面 + 本局未用过；
- **下蹲**：`crouch` 连续 2 帧进入切换，离开连续 8 帧后才允许下一次切换；
- **暂停 / 继续**：`two_fingers` / `one_finger` 的上升沿。

键盘回退与手势共用同一套"请求"变量（`jump_requested` / `double_requested` / `crouching`），互不干扰。

## 4. 物理与碰撞

| 对象 | 尺寸 / 行为 |
|------|-------------|
| 角色 | 36×44 px，下蹲 24 px；脚底锚定，改变高度时保持脚底不动 |
| 柱子 | 20×60 px，命中盒 14×52 px（比视觉更宽容） |
| 蹲墙 | 30×185 px，底留 40 px 缺口 |
| 平台 | 1600×14 px，顶面高出地面 160 px；平台下方还有半高柱与一根"贴平台底部"的蹲墙 |

关键实现：

1. **扫掠落地**（`current_ground`）：只有当上一帧脚底在平台顶面之上、下一帧脚底到达/越过顶面时才判定落上，避免高速下落穿过 14 px 薄平台；
2. **顶头反弹**：上升阶段若头部穿过平台底面，则将 `vy` 归零并贴回平台底部，不触发死亡；
3. **受击反馈**：撞到障碍扣 1 命 + 18 帧屏幕红闪 + `hurt` 音效，随后 90 帧（约 1.5 秒）内穿过该障碍不再扣命，避免同一障碍瞬间清空血量；
4. **计分**：障碍完全移出屏幕左侧 +1 分，因此分数≈越过的障碍数，与跳跃技巧弱相关、与生存时间强相关。

物理常量集中在 `game/main.py` 顶部（`GRAVITY`、`JUMP_V`、`PLAYER_*`、`WALL_*` 等），调整手感只需改这些数字。

**音频**：全部由标准库 `wave` + `math` 合成（22050 Hz 单声道），包括跳跃 / 二段跳 / 下蹲 / 暂停 / 继续 / 过关 / 失败 / 受伤 8 个音效与 1 段 C–Am–F–G 琶音循环 BGM；音量分别为 BGM 0.6、普通音效 0.7、下蹲低频 0.3（避免轰耳）。`pygame.mixer` 初始化失败时静默降级，不影响游戏运行。

## 5. 关卡与生成

- **闯关模式**使用固定序列：`3 柱 → 蹲墙 → 柱 → 蹲墙 → 间隔 → 平台 → 终点旗`（`PATTERN`），保证每次演示一致；
- **平台段**：2.5 屏（1600 px）窄桥，桥面上有 2 个单红块（`WIDTH+400 / +900`）与末端三连红；桥下是 2 根半高柱（`WIDTH+170 / +420`）和 1 根贴着平台底部的蹲墙（`WIDTH+700`），走地面路线必须下蹲通过；
- **无尽 / 限时模式**按固定权重随机生成柱子与蹲墙，生成间隔由当前难度决定（简单 155 帧 / 标准 115 帧 / 困难 85 帧）；
- **限时模式**相同玩法，60 秒倒计时结束即结算；
- 三档难度通过"滚动速度 / 生成间隔 / 生命数"区分：简单 6 命、标准 5 命、困难 3 命。

## 6. 数据格式（本地存档）

`game/save.json`（运行时生成，已在 `.gitignore` 中忽略）：

```json
{
  "slots": {
    "1": {"mode": "level", "diff": "normal", "best": 12},
    "2": {"mode": "endless", "diff": "hard", "best": 95}
  },
  "active": "2",
  "points": 242,
  "owned": ["green", "neon", "ice"],
  "skin": "ice"
}
```

- 10 个槽位，未使用的槽位 `best = 0`；
- `points` 为商城积分，通关/结束时按分数累加；
- `owned` 为已解锁皮肤；`skin` 为当前皮肤；
- 读取时做兼容过滤：旧存档里不存在的皮肤会被丢弃，`skin` 不在皮肤表里时回退到 `green`。

## 7. 性能预算

| 项目 | 数值 |
|------|------|
| 逻辑分辨率 | 640×480（`pygame.SCALED` 全屏放大） |
| 目标帧率 | 60 FPS（帧预算 16.7 ms） |
| 单帧手势推理 | 实测 ≈9 ms（640×480），在独立线程 |
| 主循环耗时 | 远低于 16.7 ms（纯 2D 绘制，无贴图解码压力） |

复杂度控制：障碍数量随屏幕滚动增删，最多几十个；背景用程序化渐变与多边形绘制，没有大图解码；音效在启动时一次性加载。

## 8. 关键取舍

| 取舍 | 选择 | 理由 |
|------|------|------|
| 识别方案 | MediaPipe 预训练模型 + 几何规则 | 免训练、CPU 实时、可解释、易调参 |
| 游戏引擎 | Pygame | 2D 平台游戏足够、依赖轻、跨平台、学习成本低 |
| 手势语义 | 一动作一手势 | 共用基础手势 + 位置/朝向微差在真实摄像头下不稳定 |
| 失败惩罚 | 5 命 + 受击无敌窗口 | 演示成功率高，同时保留挑战与反馈 |
| 存档 | 单个 JSON 文件 | 无需数据库，便于备份与调试 |
| 网页版 | 不做 | Pygame 不能直接跑在浏览器，重写引擎风险高、无法验证摄像头手感 |

## 9. 可扩展点

- `PATTERN` / 关卡生成：外置为 JSON 关卡数据；
- `Player.draw` / `get_sprite`：皮肤系统与自定义贴图；
- `tools/gen_sounds.py`：调整音色与 BGM 和弦进行。
